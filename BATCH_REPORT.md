### Design decisions taken in this batch (please confirm)

1. **Current time segment only.** `ZEAM_I_Equipment` filters `ValidityEndDate = '99991231'`,
   so `Equipment` alone is the key. The equipment history (time segments) is left out for
   now; candidate for Batch 5 (`ZEAM_I_EquipmentTimeSegment`).
2. **No DCL for transient queries.** `ZEAM_C_*Q` carry `@AccessControl.authorizationCheck: #NOT_ALLOWED`
   and are listed in `no_dcl_by_design`. This deviates from hard rule 5 ("every view gets a
   DCL"). As far as we know, a role cannot be defined on a transient entity, and the
   analytical engine applies the provider's (cube's) DCL. Revisit if activation proves otherwise (GEN-Q01).
3. **DCL inheritance from SAP roles** instead of our own PFCG mappings. This depends on the
   SAP roles' element names (EQ-D01, FL-D01, HIGH).
4. **Text views: unrestricted role** (explicit `grant select on ...;`), like SAP's own
   text views, which do not check authorization.
5. **`FuncLoc` abbreviation** in object names, so a prefix up to 6 characters still fits in 30
   (`ZEAM_I_FunctionalLocationText` would have been 29 characters).
6. **Flat package.** All objects go in `ZEAM_VDM` (no sub-package per module). Test classes
   live in `/tests/abap` and are copied into `src/` only with `--with-tests`.
7. **DDLX layer `#PARTNER`.** It suits a sold add-on, and customers can still override in
   `#CUSTOMER`.
8. **Measures on master data.** The cubes use a constant counter (`NumberOfEquipments`,
   `NumberOfFunctionalLocations`). The equipment cube also has `AcquisitionValue`
   aggregated per currency.

### Design decisions taken in this batch (please confirm)

1. **Open/closed flags are derived in the basic views.** `MaintNotifIsOpen` comes from the
   notification processing phase (1-3 = open). `MaintOrderIsOpen` comes from an empty technical
   completion date. Both depend on unconfirmed element names (NT-005, MO-004). The fallback is
   the system status (JEST: I0045 TECO / I0072 NOCO) via a released status view. That would
   change one expression per view.
2. **Operation and component views are fact-like basic views** (no `#DIMENSION`). They have an
   association `[1..1]` to the order header in the same module. The cubes take header
   characteristics over through path expressions, so they need no join.
3. **Reference objects stay plain fields.** Equipment, functional location, notification and
   maintenance plan on the order (and the same on the notification) are not associations in the
   base views. The associations live in link views, so `maintenance_order` can be bought without
   `equipment`.
4. **Notification ↔ order link uses the order number on the notification** (QMEL-AUFNR). Object
   lists (several notifications per order) are not covered yet (LNK-003).
5. **Open component quantity** is computed as requirement minus withdrawn quantity, never
   negative, in the base unit.

### Design decisions taken in this batch (please confirm)

1. **First real hard dependency.** `measurement_document` needs `measuring_point`. The reading
   cube gets the measuring point category, unit and reference object through `_MeasuringPoint`.
   Selling readings without measuring points would make no sense.
2. **Readings are FLTP in SAP.** The cube converts them with `fltp_to_dec(... as abap.dec(31,6))`
   and offers minimum / maximum (no sum). The unit is the measuring point's
   `MeasurementRangeUnit` (characteristic). Cancelled documents are excluded in the cube, not in
   the basic view.
3. **Maintenance plan and item share one module.** Items are the reference-object level of a
   plan. The plan → item association `[0..*]` and item → plan `[0..1]` are inside the module, so
   no link view is needed.
4. **Task lists return all change versions** (PLKO/PLPO counters). Restricting them to the
   current version needs a reliable "valid today" rule. That is left open (TL-004), and the
   item → task list link is therefore to-many.
5. **No DDLX** for the measuring point, reading and task list cubes. These are purely analytical
   and have no list-report use case yet.
